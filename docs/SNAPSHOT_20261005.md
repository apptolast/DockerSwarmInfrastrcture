# Promoción del snapshot Ubuntu 20261005

Prerrequisito de mantenimiento, sin aplicación al servidor. El snapshot
`20260924T000000Z` sale del SLO de 14 días el 2026-10-08 a las 00:00 UTC:
desde entonces `scripts/validate-host-security.py` falla en cualquier rama
con `Ubuntu snapshot exceeds the 14-day promotion SLO`. Se mantiene ese
límite y todos sus guards; solo se mueve el punto revisado del archivo.

## Evidencia obtenida

Contenedor efímero Ubuntu 26.04 con la misma imagen oficial que las dos
promociones anteriores:
`ubuntu@sha256:2260313b31c8c011cd2eebe728008efac1b3982be73eb71348ea2648d2c0e09b`.
Se instaló `ca-certificates` antes de verificar HTTPS; ese primer
`apt-get update` no cuenta como verificación. Después se vaciaron las listas
y se ejecutó `apt-get update --snapshot 20261005T000000Z` con
`APT::Update::Error-Mode=any`: EXIT 0 sin errores de descarga.

Respecto a la promoción anterior, los scripts registran el código de salida
real de cada paso y del contenedor, comprueban el código de salida de `gpgv`
para cada InRelease en vez de filtrar su salida, exigen la huella de la clave
de archivo en esa salida, guardan la salida completa de
`apt-cache policy` y la orden exacta de `docker run`.

Los InRelease del snapshot se verificaron con `gpgv` y el keyring oficial
incluido en Ubuntu; firma válida de la clave de archivo Ubuntu 2018
`F6ECB3762474EDA9D21B7022871920D1991BC93C` en todos. APT verificó los índices
Packages contra esos metadatos firmados.

SHA256 de InRelease por suite:

- resolute:
  `45F95CE276CDBA3E41870516A130E03C58B8B7A79E9546B0EFE9E526D255740C`
- resolute-updates:
  `B01932D3A6C1796A9EE7428ED58300B6CC288E0DFC004337C408AE865007D19E`
- resolute-security:
  `578358F7B5E41AD069FC209BFA8AB45410F24D241BE80255BDD94DBF3C11DC98`
- resolute-backports:
  `87A479FEAA85FD2C2781669468C0919591ACC60EE725ACDF870D54491272281D`

El InRelease de `resolute` coincide byte a byte con el de las promociones
anteriores, como corresponde a la suite de release congelada.

APT policy con `APT::Snapshot=20261005T000000Z` mostró un candidato nuevo,
que se fija:

- `curl=8.18.0-1ubuntu2.7` (antes `8.18.0-1ubuntu2.5`)

Los otros doce pins Ubuntu conservan su versión, que sigue siendo la
candidata del snapshot. La simulación conjunta
`apt-get -s --snapshot 20261005T000000Z install --no-install-recommends` de
los trece pins terminó EXIT 0 con 111 líneas `Inst` y resolvió `curl` y su
dependencia `libcurl4t64` en `8.18.0-1ubuntu2.7` desde `resolute-updates` y
`resolute-security`. No se instala nada ni se simula contra el host
productivo. CrowdSec pertenece a su repositorio externo: sus dos pins y su
clave no cambian y esta prueba no acredita ese repositorio.

Scripts, órdenes, códigos de salida y salidas originales preservados fuera
del árbol en `deployment-preparation/ax-snapshot-20261005/` (`verify.sh`,
`verify.command`, `verify.exit`, `verify.log`, `simulate.sh`,
`simulate.command`, `simulate.exit`, `simulate.log`).

No cambian `services.yml`, el marcador de restauración, el SLO, el reloj ni
la configuración de SSH. Aplicar el snapshot al host es una operación
aparte del playbook `host-baseline`, fuera del alcance de este cambio: hasta
entonces el host sigue en `20260924T000000Z`, el snapshot con el que se
aplicó «Parcheo del sistema operativo» el 2026-10-05. Ese apply instala el
pin de `curl`; los paquetes sin pin que el snapshot nuevo traiga más nuevos
se instalan en la siguiente ventana de parcheo
([OPERATIONS.md](OPERATIONS.md), «Parcheo del sistema operativo»).

[Servicio oficial de snapshots](https://snapshot.ubuntu.com/) documenta la
selección explícita por fecha. Esa documentación no sustituye firmas y pins.
